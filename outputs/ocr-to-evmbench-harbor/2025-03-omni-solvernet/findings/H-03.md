# [H-03] Fixed close buffer allows filled orders to reclaim deposits during portal downtime

## Affected code

- `contracts/solve/src/SolverNetInbox.sol`: `CLOSE_BUFFER` and `close`

## Root cause

`close` treats an order as safely refundable after a fixed six-hour buffer,
checking only the local order status and deadline. It does not check whether
the Omni Portal or the destination route is paused. If the destination fill
already happened but the acknowledgement is delayed by network downtime or a
paused portal, the local status remains `Pending` and the owner can close it.

## Prerequisites

- The order was executed on the destination chain.
- The source acknowledgement is delayed beyond six hours by Omni downtime or
  a paused route.

## Exploit sequence

1. A solver fills the order and the destination chain holds the resulting
   execution, but the source-chain `markFilled` message cannot arrive.
2. The source inbox remains `Pending` because `close` has no portal-state
   check.
3. Once `fillDeadline + CLOSE_BUFFER` passes, the order owner calls `close`.
4. `_transferDeposit` returns the source deposit despite the destination fill.

## Impact

The order owner receives both the destination-chain result and the source
deposit. The protocol loses the deposited assets whenever the acknowledgement
is delayed beyond the fixed buffer.

## Code evidence

The audited `close` implementation checks `Status.Pending`, caller ownership,
and `header.fillDeadline + CLOSE_BUFFER`, then calls `_transferDeposit`; it
does not query `OmniPortal` pause state. `CLOSE_BUFFER` is a fixed six hours.

## Remediation

Check global, `xsubmit`, and route-specific portal pause state before allowing
closure, and pause or otherwise protect close while acknowledgements are
unavailable. The cited remediation adds an `IOmniPortalPausable.isPaused`
check.
