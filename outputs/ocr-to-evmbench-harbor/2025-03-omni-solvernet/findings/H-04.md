# [H-04] Reentrant middleman callbacks steal in-flight token or native balances

## Affected code

- `contracts/solve/src/SolverNetMiddleman.sol`: `executeAndTransfer`

## Root cause

`executeAndTransfer` calls an arbitrary target before transferring the selected
token balance to the requested recipient. The target can call back into the
permissionless middleman while the outer operation is in progress. The inner
call can direct `safeTransferAll` to the attacker and drain the middleman's
balance before the legitimate outer transfer executes.

## Prerequisites

- A middleman operation has a token or native balance available during target
  execution.
- The target or a callback it invokes can call the middleman again.

## Exploit sequence

1. A user invokes `executeAndTransfer` for a token and recipient.
2. The target call executes arbitrary code and reenters
   `executeAndTransfer` with the attacker as `to`.
3. The reentrant call runs `safeTransferAll` and transfers the available
   balance to the attacker.
4. The outer call then transfers an empty or reduced balance to the intended
   recipient.

## Impact

An attacker-controlled callback can redirect token or native assets held by the
middleman, causing the intended recipient to lose the entire in-flight
balance. This is a direct asset-loss path, not merely a permissioning concern.

## Code evidence

At the audited commit, `executeAndTransfer` is external, payable, and has no
reentrancy guard. It performs `target.call{value: msg.value}(data)` at line 17
before `safeTransferAll` at lines 20–21. The cited remediation replaces the
initializer base with `ReentrancyGuard` and marks this function `nonReentrant`.

## Remediation

Guard the whole execute-and-transfer sequence against callbacks, and preserve
the intended recipient and token accounting across the external call.
