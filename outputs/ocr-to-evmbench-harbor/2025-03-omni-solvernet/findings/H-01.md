# [H-01] Reentrant fill acknowledgement lets a filled owner reclaim the source deposit

## Affected code

- `contracts/solve/src/SolverNetInbox.sol`: `open`, `close`, and `markFilled`
- `contracts/core/src/xchain/OmniPortal.sol`: `_exec` and `_call`

## Root cause

`SolverNetInbox.markFilled` uses the same `ReentrancyGuard` as user-entry
points. While `open` is transferring an ERC-20 deposit, a malicious token can
reenter `OmniPortal.xsubmit`. The portal reaches `markFilled` while the inbox
guard is entered, so the acknowledgement reverts. `OmniPortal._exec` increments
the inbound message offset before performing the call and records a failed
`XReceipt` instead of reverting the submission, so the acknowledgement cannot
be retried.

## Prerequisites

- An order is filled on its destination chain but its source-chain
  acknowledgement is still pending.
- An attacker can use a token callback during `open` or an expired old order
  during `close` to enter the protocol before `markFilled` executes.

## Exploit sequence

1. The attacker opens an order using a callback-capable token, or calls
   `close` for an older pending order after its close buffer.
2. During that external token transfer, the attacker submits the pending
   cross-chain message.
3. `OmniPortal._exec` calls `SolverNetInbox.markFilled`, which reverts because
   the inbox reentrancy guard is already entered.
4. The portal advances the message offset and emits a failed receipt, so the
   fill state remains `Pending` and the message is consumed.
5. After `fillDeadline + CLOSE_BUFFER`, the order owner calls `close` and
   receives the source deposit even though the destination execution already
   delivered the order's assets.

## Impact

The attacker can obtain both the destination-chain fill and the source-chain
deposit. The protocol loses the deposited native or ERC-20 assets.

## Code evidence

At the audited commit, `markFilled` is declared `external xrecv nonReentrant`.
`open` calls `_processDeposit`, which invokes arbitrary-token
`safeTransferFrom`, while `close` uses the same guard and `_transferDeposit`.
In `OmniPortal._exec`, `inXMsgOffset` is incremented before `_call`, and the
call result is emitted as `XReceipt(success, errorMsg)` without reverting on a
failed user call.

## Remediation

Do not apply the inbox reentrancy guard to the cross-chain acknowledgement, or
otherwise make acknowledgement execution independent of user-entry locks.
The cited remediation removes `nonReentrant` from `markFilled`.
