# [H-02] Liquidation transfers use total token supply and seize excess collateral

## Affected code

- `src/ERC721WrapperBase.sol`: `transfer`, `balanceOf`, and `normalizedToFull`

## Root cause

For every enabled `tokenId`, `transfer` converts a requested unit-of-account
amount into ERC-6909 units with
`amount * totalSupply(tokenId) / balanceOf(sender)`. The numerator uses the
global supply even when the sender owns only a fraction of that `tokenId`.
The conversion must use the sender's actual per-token balance.

## Prerequisites

- A borrower owns less than the full ERC-6909 supply of at least one enabled
  collateral `tokenId`.
- A normal transfer or an Euler liquidation invokes the wrapper's
  unit-of-account `transfer(address,uint256)` entry point.

## Exploit sequence

1. The borrower splits one wrapped position with another account while keeping
   that `tokenId` enabled as collateral.
2. `balanceOf(sender)` values only the borrower's fractional holdings.
3. During liquidation, `normalizedToFull` nevertheless multiplies the requested
   value by the entire `tokenId` supply.
4. The wrapper transfers more ERC-6909 units than correspond to the requested
   liquidation value, or reverts when the inflated amount exceeds the
   borrower's balance.

## Impact

A liquidated borrower can lose more collateral than the liquidator is entitled
to receive. The same inflated calculation can also block liquidation and allow
bad debt to accrue when the borrower lacks the overstated token amount.

## Code evidence

At the audited commit, `ERC721WrapperBase.sol:87-96` loops over every enabled
`tokenId` and calls `normalizedToFull`. Lines 176-178 multiply by
`totalSupply(tokenId)` rather than `balanceOf(sender, tokenId)`. The cited fix
commit `b7549f2700af133ce98a4d6f19e43c857b5ea78a` adds the sender parameter and
uses that sender's actual token balance.

## Remediation

Normalize each transfer against the sender's per-token ERC-6909 balance, then
apply an explicit receiver-favoring rounding policy for liquidation transfers.
