# [H-01] Missing nonce validation allows EIP-712 subscription replay and double asset transfers

## Affected code

- `contracts/on-ramp/SecuritizeOnRamp.sol`: `executePreApprovedTransaction`, `hashTx`, `noncePerInvestor`

## Root cause

`SecuritizeOnRamp.executePreApprovedTransaction` recovers an EIP-712 signer and
checks that the signer has the EXCHANGE or ISSUER role, then increments
`noncePerInvestor[txData.senderInvestor]` and executes the approved call.
`hashTx` includes `txData.nonce` in the signed digest, but the function never
requires `txData.nonce == noncePerInvestor[txData.senderInvestor]`.

Because only the signed payload is checked, any previously valid signature for
an older nonce remains valid forever. Each successful call still increments the
stored counter, so replays do not even need to forge a new signature or match
the current counter.

## Prerequisites

- A valid EXCHANGE or ISSUER EIP-712 signature over an
  `ExecutePreApprovedTransaction` that spends investor liquidity / mints or
  transfers DS tokens (for example a prior `subscribe` / swap authorization).
- The on-ramp is not paused.
- The investor still has sufficient USDC (or other liquidity token) allowance
  and balance for another execution of the same calldata.

## Exploit sequence

1. An authorized issuer/exchange signs an investor subscription or swap
   transaction with nonce `N` (commonly `0` for a first purchase).
2. Anyone submits `executePreApprovedTransaction(signature, txData)` once; the
   call transfers investor liquidity and delivers DS tokens, then increments
   the stored nonce to `N+1`.
3. The attacker replays the **same** `signature` and `txData` (still carrying
   nonce `N`). Signature recovery and role checks succeed because `hashTx`
   still hashes the caller-supplied `txData.nonce`, not the stored counter.
4. The on-ramp executes the destination call again: another liquidity debit and
   another DS-token credit. The stored nonce advances again even though nonce
   `N` was reused.

The Cyfrin report includes a Hardhat proof of concept that shows balances and
`nonceByInvestor` after a successful replay (double DS tokens, drained USDC,
nonce advanced to `2` after replaying nonce `0`).

## Impact

Direct loss of investor assets. Each replay can pull additional stablecoins from
the investor and mint or transfer additional DS tokens without a fresh
authorization. Accounting and custodian flows that assume one signed approval
equals one purchase are broken.

## Code evidence

At audited vulnerable commit `a944bb11b106c13a5e43f8de01c9c01eeb5bb472`:

```solidity
function executePreApprovedTransaction(
    bytes memory signature,
    ExecutePreApprovedTransaction calldata txData
) public override whenNotPaused {
    bytes32 digest = hashTx(txData);
    address signer = ECDSA.recover(digest, signature);

    IDSTrustService trustService = IDSTrustService(dsToken.getDSService(dsToken.TRUST_SERVICE()));
    uint256 signerRole = trustService.getRole(signer);
    if (signerRole != trustService.EXCHANGE() && signerRole != trustService.ISSUER()) {
        revert InvalidEIP712SignatureError();
    }
    noncePerInvestor[txData.senderInvestor] = noncePerInvestor[txData.senderInvestor] + 1;
    Address.functionCall(txData.destination, txData.data);
}
```

`hashTx` encodes `txData.nonce` into the EIP-712 struct hash but that value is
never compared to `noncePerInvestor[txData.senderInvestor]` before the
increment and external call.

Securitize fixed the issue in commit
`65179bcf41ed859106069dcaa751f5a2cec3038e` by hashing the **stored** nonce
(`noncePerInvestor[txData.senderInvestor]`) instead of `txData.nonce`, so a
replayed signature no longer matches the digest. That fix is intentionally not
the task snapshot.

## Remediation

Before executing, require the signed nonce to equal the current per-investor
nonce (or bind the digest exclusively to the stored nonce and reject stale
signatures). Increment only after a successful validation, and cover replay in
tests.
